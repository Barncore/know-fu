# Capability acceptance contract

This contract was set on 4 October 2026, before any results from the progressive-reading comparison came in. It puts the [north star](NORTH_STAR.md) into checkable terms. Results belong in [VALIDATION.md](VALIDATION.md). Private case wording, rubrics, model traces and canonical snapshots stay out of the public package.

## Behaviors and evidence

| Use | Required behavior | Decisive failure |
|---|---|---|
| Explain | A connected mechanism, the relevant unit, and a condition that changes the explanation | Conflating different statistical questions, or erasing a precondition |
| Teach | Start from prerequisites, work a concrete case, address a tempting misunderstanding, check understanding | Teaching that an omnibus rejection means every pair differs, or that non-rejection means equivalence |
| Apply | Run the decision procedure on unfamiliar inputs and explain its limits | A wrong rejection set, an incorrect stopping rule, or an invalid independent sample size |
| Compare | Keep both positions, and compare definitions, evidence and scope | Choosing a winner with incompatible metrics or unsupported error-rate claims |
| Invent | Combine supported mechanisms with an explicit new inferential step and a discriminating test | Presenting the proposed transfer as an established result from the source |
| Synthesize | Cover the decision pipeline, important branches, exceptions and evidence limits | A coherent overview that silently drops a decisive condition |
| Investigate | Find the missing evidence that could change the decision, and prioritize a feasible next check | Inventing current evidence, or treating a sparse graph as a valuable gap |
| Learn cumulatively | Later complementary and qualifying sources change the affected procedures, teaching and questions, while keeping each source's own account | Only appending new records, or silently rewriting an earlier author's position |
| Preserve knowledge | Earlier unaffected cases still work after reweaving | Losing a correct stopping rule, an exact-source discrepancy or an access restriction |

## Comparison design

The preserved Demšar pilot release has 109 canonical records. The hashes of every exact record and body were frozen before new cases were designed. Its six original cases are now exposed engineering regressions. Separate acceptance prompts were written after that freeze, with rubrics grounded in the sources and withheld from both the solver and the library. The coordinator who read the sources also designed and reviewed the cases, so this is not an independent blind benchmark.

For access structure, the canonical release and page bodies stay identical. The comparison runs the original fixed full packet against progressive reading with and without optional graph exploration. Both progressive routes keep the canonical material-context checks. Every condition uses the same configured model, reasoning effort, word limit and cumulative input ceiling. Each run records measured total input, cached input, output, latency, delivered evidence, selected summaries, actual account and section reads, and unmet requirements. The input ceiling is checked after completion; it is not a hard token cutoff.

Seven task groups cover the uses above. The decisive application and exception cases are repeated to expose variability, and repeats are not independent tasks. Grading against the sources reports each quality dimension separately. Every decisive failure, every dispute over a source or rubric, and every material difference between conditions is reviewed against the original evidence. A good aggregate can't cancel out a missed condition.

Adoption as the default requires no unresolved decisive factual or condition failure, adequate completeness for every task group, and useful reading efficiency on narrow tasks. In concrete terms, the candidate has to use less measured input than the fixed packet on at least two narrow task groups without losing their quality requirements. Broad synthesis may cost more; report that trade-off instead of excluding it. A result over the shared input ceiling is descriptive evidence, not a matched-budget win. If the optional graph shows no advantage, that is not a failure of the library architecture.

For cumulative knowledge, keep the foundational source, add Bengio and Grandvalet's account of cross-validation variance, then Benavoli, Corani and Mangili's qualification of mean-rank post-hoc testing. Read each original before integrating it. Compare frozen before-and-after tasks about those boundaries and an unfamiliar application, with original-passages-only and no-library controls where they help. Repeat unaffected procedures. The result has to show which understanding changed, which earlier explanation or teaching route was revised, and what is still unknown. A small demonstration on public papers doesn't show domain mastery, or readiness to ingest arbitrary books in production.

## Release checks

The engineering checks cover scoped metadata, exact history, withdrawal propagation, pending reassessment, low-ranked caveats, stable section boundaries, stale views, changed staging, publication recovery, reading budgets, isolation and immutable resumption of evaluations. Confirm real installed MCP discovery, selected reading, access to source images, and the guides. Verify the owned plugin and packaged contracts, review staged paths and content for private material, then publish the approved release. Binding the production library and large historical migrations are separate work.

Version 1.2.0's `kb_recall` was judged against this contract's cases with a blind A/B comparison rather than the version 3 evaluator; [VALIDATION.md](VALIDATION.md) records how and why.
